# Direct source-file evidence

Use `documents_attach_source_evidence` when the user has provided a new file to attach to an existing expense or accounting entry. Select the target’s company, identify the target, pass the authorized connector file and set `set_main_attachment` only when the user wants that file selected for the native viewer. Existing evidence is retained.

The top-level `file` schema follows the [official connector file-input contract](https://developers.openai.com/plugins/reference): required `download_url` and `file_id`, declared optional `file_name` and `mime_type`. The descriptor lists `file` in `openai/fileParams`. The connector supplies the reference; neither the model nor the user needs to paste base64. Optional `byte_size` and `sha256` can bind a known source fingerprint. Filename/MIME may come from the host file metadata or download response. If neither supplies the original filename, use `original_filename`; it cannot rename a known source. Missing or generic MIME is inferred by native Odoo, disclosed as `mime_inferred` in the result and verified against persisted evidence. Contradictory declared filenames or specific MIME types are refused.

Files are bounded to 20 MiB. HTTPS download references are resolved to public addresses and pinned for each request; redirects are revalidated. Odoo credentials are never forwarded to the file host. An expired, incomplete or oversized transfer produces no Odoo mutation. Sources are not recompressed, resized or converted; persisted native content and MIME are checked before commit. A native MIME safety conversion that cannot preserve the stated source type is refused rather than silently relabeled.

For a local stdio client, configure `MCP_EVIDENCE_FILE_ROOTS` as a platform path-delimited list of explicit source directories and supply a `file:` download reference within one root. Real-path checks reject symlink escape. HTTP/OAuth connectors cannot read local filesystem references. Docker deployments must mount only the intended source directories; do not enable a broad filesystem root. Local source changes during reading require a fresh handoff.

Success returns the owned attachment ID, direct business-record URL, exact fingerprints and native provenance. The source remains usable through Odoo’s normal attachment/viewer immediately, even when the Documents archive is pending or excluded by its normal policy. External archiving is asynchronous and is not claimed complete by upload. Repeating the same target/name/MIME/content reuses the owned attachment; physical binary deduplication also applies when the same bytes are attached to a different authorized record. Different filenames remain distinct evidence rows.

One tool action calls one native mutation, without automatic transport retries. Native Odoo may retry a conflicting database transaction internally: first creation advances the authorized target's audit version while retaining its current main attachment, so the retry can see and reuse the first committed file. It does not download the source again. On unknown completion, inspect target attachments by filename, size and native checksum, then compare the main attachment before deciding whether to retry. Never reuse an expired download reference blindly. This action appends evidence and an attributable note; it does not change financial fields or submit, approve, post, pay or reconcile the record.

Deployment requires the Distribution’s native `attach_source_evidence` methods on both supported models. The tool stays unavailable until the native application surface confirms the method. Refresh the connector manifest after deploying the qualified pair. Local SDK/schema and native byte tests qualify the implementation; they do not claim a hosted connector has already been refreshed.
